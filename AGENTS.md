# Codex Rules — Personal Life Planner v2.0

Read `docs/PRD.md`, `docs/DOMAIN_RULES.md`, `docs/API_CONTRACT.md` and `docs/DATA_MODEL.md` before implementing **each** numbered task, except when the task qualifies for **Lightweight mode** below. If files are missing, explain it; do not silently use previous v1 files. These documents are normative. The numbered prompt determines **scope**, not a license to contradict domain contracts. Do not reintroduce the old single `goal_kpis` model or `combinedProgress` averaging behavior. Implement changes, not merely plans.

## Fixed technical choices
- Monorepo `backend/` + `frontend/` + `docs/` + `data/` (gitignored), Maven wrapper, Java 21, stable supported Spring Boot 3.5.x patch pinned at initial creation, Spring Web, Validation, Spring JDBC/JdbcClient, SQLite Xerial JDBC, SQLite-compatible Flyway modules where required.
- React + TypeScript + Vite, React Router, Persian RTL, Jalali date components, no runtime external CDN/API. Multi-user with authentication, local-first.
- Backend packages are global layers (not per feature): `controller/` (all controllers + PATCH body readers), `service/` (all services and pure domain logic such as `ProgressCalculator`), `repository/` (all JDBC repositories), `model/` (domain records, `*Limits` constants), `model/enums/` (every enum), `model/vo/` (input objects, class name ends in `VO`, e.g. `CreateGoalVO`), `model/srv/` (output objects, class name ends in `Srv`, e.g. `GoalSrv`); infrastructure in `config/`, `exception/`, `util/`, `db/`. No feature sub-packages, no artificial microservices. JSON field names are unaffected by these class names. Tests: unit tests in the package of the class they test, DB tests in `db`, API/restart tests in `integration`, end-to-end in `e2e`.
- UUID text IDs; SQLite snake_case and JSON camelCase; API prefix `/api/v1`; error `{code,message,details?}`. Use REST semantics, finite decimal validation, parameterized SQL, transactions, Flyway versioning.
- Date-only Gregorian ISO `YYYY-MM-DD`; timestamps UTC ISO. Never serialize UI date-only via `Date.toISOString()`. UI week Saturday-Friday.
- Backend binds by default to `127.0.0.1` and CORS limited to local dev origin; there is no TLS, so don't expose it on a LAN/Internet. Server sync remains out of scope.
- Authentication (Spring Security OAuth2 resource server): every API path except `/health` and `POST /auth/{register,login,refresh,logout}` needs `Authorization: Bearer <access token>` (RFC 6750; 401 with `WWW-Authenticate` and the `{code,message}` body). Access token = JWT HS256, header `typ=at+jwt`, claims `iss,sub,aud,iat,exp,jti,client_id` (RFC 7519/9068), 15 min — **temporarily non-expiring** (no `exp`) via `planner.auth.access-token-expires=false`; set it to `true` to restore the 15-min TTL — key generated once and stored in `signing_keys`. Refresh token = 256-bit opaque value, stored only as SHA-256 hash, sent only as an httpOnly `SameSite=Strict` cookie on `/api/v1/auth`, rotated on every refresh with reuse detection (family revocation), absolute session lifetime 30 days. Passwords BCrypt (8..72 bytes), login throttled, login errors never reveal whether an e-mail exists. Frontend keeps the access token in memory only (never web storage) and refreshes on 401 once (single-flight).
- API documentation: springdoc OpenAPI 3.1 at `/v3/api-docs`, Swagger UI at `/swagger-ui.html`. Every new endpoint needs `@Operation(summary, description)`, operation-specific `@ApiResponse`s (404/409/429…; 400/401/500 and the `ApiErrorSrv` body are added globally by `OpenApiConfig`), `@Parameter(description)` on every parameter, a swagger `@RequestBody(description)` (PATCH: with `schema = Update…VO`), and every VO/Srv record and field needs `@Schema(description, example, allowableValues for code strings)`. `OpenApiDocumentationTest` fails otherwise. Public endpoints carry an empty `@SecurityRequirements`.
- UI: page designs are the images in `ui/` (dashboard `9a643a2d-….png`, `goal.png`, `focus item.png`, `weekly plan.png`, `today plan.png`); follow them, but data always comes from the API. Dark theme by default (☀ toggles light), bundled Vazirmatn font. Full-height pages (`/dashboard`, `/goals`, `/focus`, `/weekly`, `/today`, `/archive`, class `page--wide`) never scroll as a whole on desktop: only their inner region (card body, table, Kanban column) scrolls, with sticky headers. Reuse shared pieces before writing new ones: `shared/ui` (`Icon`, `ProgressRing`, `MenuButton`, `JalaliCalendar`, `JalaliDateField`, `AsyncState`, `useApiData`), `tasks/PriorityPicker`, `planning/TodayPlanButton` / `WeekPlanButton`, `planning/KanbanBoard`. Sidebar order: داشبورد, اهداف, آیتم‌های تمرکز, برنامه هفتگی, کارها, برنامه امروز, صندوق ورودی, گزارش‌ها (soon), بایگانی, تنظیمات.
- Manual ordering is persisted with full-list `PUT` endpoints (send every item exactly once; partial/duplicate/foreign lists → 400): goal priority `PUT /goals/priority` (1 = first = right-most card in RTL, archived goals leave the order), focus items per goal `PUT /goals/{goalId}/focus-items/order` (items never move between goals there), daily plan items `PUT /plans/daily/{date}/items/order`. Drag-and-drop uses pointer events followed on `window` (mouse/pen/touch via the ⠿ handle), a ghost + placeholder, edge auto-scroll, and always has a keyboard (arrow keys on the handle) and menu (⋮) alternative; save optimistically and revert on error.
- Data ownership: root tables (`goals`, `tasks`, `focus_items`, `inbox_items`, `daily_plans`) carry `user_id`; children are owned through their parent. Every repository query is scoped to `CurrentUser` — another user's row is a 404, never visible in lists, never linkable. New tables must follow this. The first registered account claims rows created before authentication (`user_id IS NULL`).

## Strict domain invariants
1. `Goal` can be standalone; parent may be omitted, skipped granularity levels allowed, but no cycles/self-parent. Parent period granularity strictly greater than child's.
2. `Goal` may have 0..N Key Results; each KR stores baseline, target, weight>0, with append-only check-ins. `target != baseline`; current derived from check-ins or baseline.
3. `Outcome Progress` is based **only on KRs** (or inherited direct child outcomes where no own KR). `Execution Progress` is based on unique linked Task statuses. Never average Outcome + Execution; never call it `combinedProgress` or compute Goal completion from tasks.
4. Goal status remains independent of percentages. Task statuses remain `not_started`, `doing`, `done`, with optional blockedReason. Task dueDate is distinct from schedule dates. Task priority is required: `low | medium | high` (UI order پایین · متوسط · بالا), default `low`, cannot be cleared. The today Kanban column «در انتظار» is **not** a fourth status: it is a not-done task with a `blockedReason` (moving a card in asks for the reason; moving it out clears it; a done task moved in becomes `not_started`).
5. Effective Goal attribution: direct Task.goalId wins over Task's FocusItem.goalId; count task once in subtree calculations.
6. Empty/not-measured scores are `null`, never fabricated 0; exceptions: newly created KR's baseline is an explicit numeric 0% starting point.
7. `GET` operations never write; archived entities and historical records never disappear silently. Archiving never cascades (a goal's focus items/tasks stay active). Archived goals, focus items and tasks are hidden from every working page (dashboard, goals board, focus tree, weekly, today — also as goal/focus-item names on active tasks) and shown only on `/archive`, where they can be restored or **permanently deleted** (owner decision 2026-11-10). `DELETE /goals|focus-items|tasks/{id}` accepts archived entities only (409 `not_archived`). Deleting a goal removes its KRs, check-ins, milestones, history, focus items and every task linked to it or to those items, and detaches (never deletes) child goals with a `parent_changed` history entry; deleting a focus item removes its tasks; deleting a task removes its daily-plan items. Check-ins and goal history stay append-only for every non-archived goal (V10 triggers); never add another delete path.
8. Weekly Plan is **not** a Weekly Goal. No weekly capacity/plan features in Demo 0 or MVP v0 unless a minimal prerequisite is strictly required. The `/weekly` page has no entity of its own: it is the seven daily plans of a Saturday–Friday week + tasks due that week + (current week only) undone overdue tasks; «+ به برنامه هفتگی» plans a task on one day of the week. A real weekly-commitment entity waits for MVP v1.

## Execution protocol
1. Inspect repository status, code/tests/contract and numbered migrations; don't overwrite user work. Identify exactly which task is next.
2. Implement scope of ONE prompt only; minimal working prerequisites allowed. Preserve all completed slices.
3. Add or adjust migrations and DTO/service/repository/controllers/UI/tests as needed. UI data must come from persisted APIs, not mocks or static examples.
4. Ensure accessibility, loading/empty/error states, semantic markup, responsive RTL, safe transactions, predictable error messages.
5. Run and report backend tests (`cd backend && ./mvnw -o test`), frontend tests (`npm test`), typecheck (`npm run typecheck`) and build (`npm run build`). If inaccessible, mark NOT RUN with reason. Never assert success without commands. For UI work also drive the real app in a browser against a **scratch** database and scratch ports (e.g. backend `PLANNER_SERVER_PORT=18080 PLANNER_DB_PATH=<scratch>.db`, Vite `PLANNER_API_TARGET=http://127.0.0.1:18080 npx vite --port 5174`), then stop only those processes.
6. End with a report to the owner **in Persian**: implemented behavior; files changed; API/schema deltas; exact tests PASS/FAIL/NOT RUN; smoke-test instructions (incl. whether the backend must be restarted for new endpoints/migrations); remaining limitations and backend gaps; reviewable diff summary. Keep `README.md` (manual checklist + endpoint table) and `docs/IMPLEMENTATION_STATUS.md` (feature rows, test baseline, migration list) up to date.
7. Do not commit, push, publish, or deploy unless the user separately requests it. Do not ask for intermediate approval inside the agreed task; present result for review.

## Lightweight mode
This section overrides the full documentation, verification, installation and reporting steps above only for small frontend-only UI/CSS changes that do not alter domain behavior, API contracts, persisted data, authentication, routing, accessibility semantics or build configuration.

- Do not reread the normative documents for an eligible lightweight task; inspect only the directly relevant code and nearby tests/styles.
- Run `npm run typecheck` and any directly related focused frontend test. Do not run the full frontend suite, backend tests, production build or browser smoke test unless the change is risky, the focused check fails, or the user explicitly requests full verification.
- Do not reinstall/restart the local application after each lightweight change. Reinstall only when the user says «اعمال کن», asks to update the running local app, or before a release handoff.
- Do not update `README.md` or `docs/IMPLEMENTATION_STATUS.md` for purely visual tweaks unless the documented behavior or manual checklist actually changes.
- Keep commentary minimal and the final Persian report to 3–5 short lines: behavior changed, files changed, and exact checks run.
- If any backend/API/schema/migration/domain change becomes necessary, exit Lightweight mode and follow the full execution protocol.
- The user can explicitly request Lightweight mode with: «حالت سبک: فقط تغییر را پیاده‌سازی کن و typecheck بگیر؛ تست کامل و گزارش مفصل لازم نیست.»

## TDD focus / data safety
- Test positive and negative cases, zero/undefined denominator, descending KR, weighted KR, archived entities, date boundaries and SQLite restart. Validate `PRAGMA foreign_keys` on every connection.
- Preserve history; prefer archival to deletes (permanent delete only through the archive rules in invariant 7). Avoid hardcoded timezone and fragile SQL schema changes.
- Migrations are forward-only (`V1`…`V10` applied; next is `V11__…`); never edit an applied one and update `MigrationCount.APPLIED`. Test upgrades from a populated older DB.
- Never write test data to the owner's `data/planner.db` and never delete it; never stop or reuse the owner's running dev servers (Vite 5173, backend 8080). Integration tests use their own `target/test-db/*.db`.

## Out of scope until roadmap milestone
MVP v1 weekly commitments/capacity/rescheduling/reviews; MVP v2 real time logging/time blocks/habits/advanced analytics; RC backup/restore/PWA hardening; cloud, mobile sync, OAuth/social login, password reset by e-mail, roles/sharing between users, AI planner, Notion/Calendar integration.
